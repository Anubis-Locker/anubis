# Два уровня доступа: admin и user

## Идея
Требование заказчика: административный доступ настраивается по умолчанию и пользователю не виден; пользовательский доступ пользователь настраивает сам.

- **Admin-уровень** — значения задаются при сборке (`src\common\brand.config.js`) или переменными окружения `ANUBIS_ADMIN_*` при (первом) запуске (например, из установщика / системной политики). Они **не показываются и не редактируются** в Settings.
- **User-уровень** — всё остальное (тема, раскладка, SSH-профили, quick commands, шрифты и т.д.) — без изменений.

## Реализация (реальная защита, не только UI)
| Слой | Файл | Что делает |
|---|---|---|
| main | `src\app\common\admin-policy.js` | Вычисляет политику (brand + env), `applyAdminPolicy(config, {partial})` принудительно проставляет значения, `getAdminLockedKeys()`, `ensureMcpToken()` |
| main | `src\app\lib\get-config.js` | При каждом чтении конфига применяет политику и передаёт в renderer `config.adminLockedKeys` |
| main | `src\app\lib\user-config-controller.js` | `saveUserConfig`: значения из IPC/UI переписываются политикой до записи в БД; `adminLockedKeys` в БД не пишется |
| main | `src\app\lib\admin-startup.js` (вызов в `create-app.js`) | На старте перезаписывает отклонившиеся значения в сохранённом конфиге, применяет автозапуск ОС и регистрацию deep link |
| main | `src\app\widgets\widget-mcp-server.js` | Подставляет MCP-токен, пользователь его не может очистить/заменить |
| main | `src\app\lib\crash-reporter.js` | Отправка отчётов об ошибках и разового heartbeat при старте — включено по умолчанию, URL/вкл.-выкл. только через admin-policy |
| renderer | `src\client\common\admin-policy.js` | `ADMIN_LOCKABLE_KEYS`, `isAdminLocked(key, config)` — для форм |
| renderer | `setting-common.jsx`, `ai-config.jsx`, `ai-presets.js`, `setting-sync-form.jsx` | Скрытие/блокировка полей («управляется администратором») |

Если пользователь правит файл/БД или вызывает `saveUserConfig` напрямую, значения будут возвращены при следующем чтении/сохранении/старте. Списки ключей в main и renderer сверяет тест `src\test\unit-ci\admin-policy.spec.js`.

## Admin-locked ключи
| Ключ | Значение по умолчанию | Как изменить (только сборка/env) | В UI |
|---|---|---|---|
| `syncSetting.cloudApiUrl` | `brand.sync.cloudApi` | `brand.config.js` → `sync.cloudApi` или `ANUBIS_ADMIN_SYNC_API` | URL скрыт, показана пометка |
| `baseURLAI`, `apiPathAI`, `authHeaderNameAI` | `brand.ai.baseURL`, `/chat/completions`, `Authorization: Bearer` | `brand.config.js` → `ai.baseURL` или `ANUBIS_ADMIN_AI_BASE_URL` | поля disabled, пресеты скрыты |
| `enableGlobalProxy`, `proxy` | не заданы (не блокируются) | `ANUBIS_ADMIN_PROXY=socks5://host:port` — тогда включаются и блокируются | блок Global proxy скрыт |
| `checkUpdateOnStart` | `brand.update.enabled` (true); серверы — `brand.update.baseUrls` (build-time) | `brand.config.js` → `update` или `ANUBIS_ADMIN_UPDATE_ENABLED=0/1` | переключатель скрыт |
| `mcpServerEnabled` (+ MCP-токен) | true; токен случайный, `userData\admin-mcp-token` | `ANUBIS_ADMIN_MCP_ENABLED=0/1`; токен — удалить файл для перевыпуска | токен в UI не показывается |
| `errorReportEnabled`, `errorReportUrl` | true; `https://api.anubis.locker/api/report` (`brand.domains.api`) | `ANUBIS_ADMIN_ERROR_REPORT=0/1`, `ANUBIS_ADMIN_ERROR_REPORT_URL` | в UI нет |
| `autoStartOnLogin` | true (только упакованное приложение) | `ANUBIS_ADMIN_AUTOSTART=0/1`; `ANUBIS_ADMIN_AUTOSTART_USER_CAN_DISABLE=1` снимает блокировку — тогда переключатель в Settings доступен | скрыт, если заблокирован |

Отправляются: при ошибке — текст/стек (до 8 КБ), версия, платформа, арх; при старте приложения — только разовый "heartbeat" (без текста/стека), чтобы `api.anubis.locker` мог показать список установленных экземпляров (`/api/installs`). Оба типа событий включают случайный `installId`, который хранится в userData (`install-id`, ничего не говорит о пользователе) — это не телеметрия использования, `brand.update.sendTelemetry` остаётся `false` (отправляется только версия при проверке обновлений).

Отчёты об аварийном завершении дочернего процесса/рендерера также отправляются серверу. Ошибки сохранения `installId`, недоступность API и некорректное подтверждение приёма записываются в локальный журнал; запрос ограничен пятью секундами. Идентификатор установки связывает её отчёты между запусками, но не содержит имени пользователя.

Административный список установок: `https://api.anubis.locker/admin`. Вход выполняется отдельным серверным `ADMIN_TOKEN` службы `anubis-mgmt-api`, а не локальным токеном MCP. Токен хранится только в памяти открытой вкладки; выход удаляет показанные данные. Доступны последний отчёт каждого профиля и его история ошибок. Один ПК с несколькими профилями имеет несколько `installId`; время разового отчёта не означает статус online.

В отдельном разделе **Managed devices** работает регистрация с индивидуальными учётными данными экземпляра. Секрет хранится локально; сервер сохраняет только его SHA-256 fingerprint. Первая регистрация имеет статус pending: администратор сверяет полный fingerprint с локальным приложением, отмечает подтверждение и нажимает Approve. Только после этого разрешён исходящий защищённый туннель. Online означает действующий аутентифицированный канал и готовность локального Web-компонента. Повторный запуск сохраняет идентичность и решение администратора; Revoke закрывает активные каналы и браузерные сессии.

Open device открывает отдельный HTTPS-поддомен `device-<UUID без дефисов>.anubis.locker`. Одноразовый билет передаётся POST-запросом и заменяется host-only HttpOnly/Secure cookie; административный токен и билет не помещаются в URL. Необходимы wildcard DNS, сертификат и WebSocket-маршруты Nginx из `services\nginx-managed-*.conf`. Входящие порты на ПК не открываются; standalone Web сохраняет собственную пользовательскую аутентификацию. Регистрационные отчёты не содержат паролей SSH/RDP/VNC и локального ключа MCP. Авторизованный трафик приложения проходит через доверенный TLS-терминирующий шлюз: это не сквозное шифрование от оператора шлюза.

В **Managed devices** показывается только фактически опубликованный шлюзом HTTPS-адрес одобренного online-экземпляра; адрес можно скопировать отдельно от доступа. Скопированный URL не авторизует другой браузер или incognito: там нужно снова войти в админ-панель и нажать **Open device**. Перед выдачей браузерного билета или MCP-токена панель заново проверяет ID, полный fingerprint, approval и online. Сообщение об авторизации браузера не подтверждает вход в приложение, рабочий терминал, RDP или VNC.

Сбой исторических startup reports не скрывает доступные managed-устройства. Если сам список managed-устройств недоступен, последние показанные данные помечаются **stale**, а действия доступа отключаются до успешного обновления. Online-устройства показаны первыми. Windows accounts/SID/session и готовность MCP не входят в inventory-контракт и не подставляются по имени компьютера или номеру версии. У совместимого Windows machine host выбор workspace находится внутри авторизованной страницы: SYSTEM использует отдельный профиль, а данные вошедшего пользователя требуют явного выбора его контекста и, при необходимости, существующего пароля приложения из этого профиля, полученного у его владельца. Это не Windows/RDP-пароль и не административный токен. Профиль без установленного пароля приложения может открыться сразу после браузерной авторизации; inventory не сообщает эту настройку. Панель не получает, не устанавливает и не сбрасывает пароли профилей.

Изменения только `services\management-dashboard.html` не требуют пересборки desktop/Web или публикации SDK. Служба читает HTML и рассчитывает CSP-хэши один раз при создании сервера: после отдельного разрешения на развёртывание требуется заменить этот файл и перезапустить management API. Перезапуск кратковременно разрывает туннели; агенты переподключаются с сохранёнными ID и approval. Браузерные сессии и временные MCP-гранты хранятся в памяти шлюза и после перезапуска требуют новой авторизации. Хранилище регистраций, отчёты, настройки службы и учётные данные не изменяются.

**MCP access** выдаёт отдельные URL и временный Bearer-токен только для `/mcp` выбранного устройства. Срок действия — не более часа; разрешены HTTP GET/POST/DELETE, но не браузерный интерфейс, API контроллера или WebSocket. Локальный аутентифицированный MCP-виджет должен быть запущен: его ключ подставляет локальный адаптер, а регистрационные данные и выдаваемый контроллером доступ этого ключа не содержат. Обычные настройки пользовательских Web-виджетов сохраняют свои существующие права доступа и модель доверенного прокси. Отключённый или неготовый MCP не считается доступным. Истечение срока закрывает активный HTTP/SSE-поток; Revoke также отзывает MCP-токены. Показанные реквизиты остаются только в открытой вкладке до закрытия секции или выхода; храните временный токен как секрет.

Начиная с desktop 5.6.12 регистрация включена по умолчанию. Идентичность сохраняется в `app.getPath('userData')\managed-access-identity.json`; статус и fingerprint доступны в нативном About. Административные переопределения: `ANUBIS_ADMIN_MANAGED_ENABLED=0` и `ANUBIS_ADMIN_MANAGED_URL` (по умолчанию `https://api.anubis.locker`). Существующий пароль desktop дополнительно защищает браузерные данные; его смена отзывает браузерные сессии, но не решение об одобрении устройства. MCP — отдельная административная возможность для уже работающего нативного хранилища, а не удалённой браузерной вкладки. Этот доступ не отключает шифрование и не разблокирует браузерные данные.

**Ограничение Windows 5.6.12:** агент и backend принадлежат процессу desktop; закрытие приложения завершает их, и устройство становится offline. Постоянная служба Windows, работа до входа пользователя и переключение SYSTEM/пользователь в этой версии не реализованы. Повышение прав установщика не меняет учётную запись приложения или PowerShell. Путь приглашения PowerShell не подтверждает права: проверять нужно SID и токен процесса. Проверки managed-доступа при открытом приложении не являются приёмкой постоянно работающего машинного агента.

В разрабатываемом Windows machine host служба SCM и headless workspace работают отдельно от пользовательского GUI; контракт и границы доступа описаны в `native\windows-host\README.md`. Изолированная проверка подтвердила SYSTEM SID `S-1-5-18`, session 0, реальный PowerShell `whoami /user`, сохранение профиля после stop/start службы и работу того же engine после закрытия и повторного открытия GUI. Подтверждён также настоящий WTS-токен вошедшего Root/session 2: отдельный тестовый профиль, реальные USERPROFILE/APPDATA, пароль и восстановление зашифрованной закладки после перезапуска. Рабочий профиль не изменялся; другой Windows-аккаунт, вход до logon и перезагрузка ОС не проверялись. Это не обновление опубликованной 5.6.12: производственный rollout и миграция идентичности устройства ещё не завершены.

После перезапуска службы GUI заново проверяет контекст через защищённый native broker, закрывает старый WebContents и использует новый endpoint/proof. Проверка с реальным GUI подтвердила переподключение без перезапуска окна и настоящий SYSTEM `whoami /user` после него. Пользовательский контекст привязан к SID и номеру WTS-сессии: замена сессии не вызывает незаметного перехода к SYSTEM или другому пользователю. Повторные попытки ограничены; после ошибки нужно явно использовать Refresh.

Machine client принимает параметры подключения, protocol URL и `.vv` как при запуске, так и от второго экземпляра. Запрос остаётся в памяти основного процесса; кнопка **Open requested connection** открывает нативное подтверждение выбранных Windows account/SID/session. До подтверждения подключение не запускается; смена контекста во время диалога отменяет отправку, а заблокированный workspace нужно сначала разблокировать. Содержимое локального `.vv` и SSH private-key файла читает интерактивный GUI, а не SYSTEM-backend: передаются параметры/байты, не путь для чтения под другой учётной записью. Максимум файла — 1 МиБ; UNC/device paths, alternate data streams, каталоги и превышение размера явно отвергаются. Парсер `.vv` общий с обычным приложением; файл с `delete-this-file` автоматически не удаляется. `--server-port` и `--batch-op` в machine client отвергаются явно, поскольку они не являются запросом подключения к выбранному workspace.

Подтверждение показывает адрес назначения без URL-пароля и предупреждает о переданном SSH private key. Исходные argv/cwd второго экземпляра передаются через Electron `additionalData`, поскольку Chromium изменяет собственный `second-instance` commandLine. Реальная изолированная проверка подтвердила cold protocol URL и второй запуск с относительным `.vv`: появились соответствующие VNC/SPICE вкладки после подтверждений, основной GUI PID не изменился. SYSTEM действительно получил отказ на чтение тестового `.vv` по ACL, но GUI интерактивного Root прочитал файл и передал параметры. Это проверка открытия вкладок и границы чтения, не успешного сетевого VNC/SPICE-сеанса. Рабочий профиль остался побайтно прежним; QA-служба и процессы удалены.

Повторный запуск через UAC передаёт один исходный запрос с корректным Windows quoting и исходной рабочей директорией; если накопилось несколько запросов, перед повышением нужно явно очистить очередь. Отказ UAC оставляет исходное окно и запрос. PowerShell для этого шага находится через фактический native Windows system directory, а не подменяемые `SystemRoot`/`PATH`. При вводе учётных данных другого администратора новый GUI работает именно под этим администратором; это не переносит чужие DPAPI-ключи и не даёт автоматически читать недоступный ему private-key файл.

Миграция managed-регистрации использует новый `managed-access-identity.json` в защищённом SYSTEM-профиле. Генерируются и новый UUID, и новый случайный bearer secret; fingerprint — SHA-256 UTF-8 hex-строки секрета, не отпечаток компьютера. Сначала появляется отдельная pending-запись; администратор независимо сверяет её ID/fingerprint и явно одобряет **новый** ID. Старый пользовательский профиль, его approval, URL и выданные browser/MCP-доступы не переносятся и автоматически не отзываются. Старый доступ можно отдельно отозвать только после проверки нового online/ready экземпляра и отдельного решения оператора. Копировать старый известный пользователю secret в SYSTEM нельзя.

Пароль профиля блокирует headless workspace и MCP до успешной проверки. После разблокировки workspace остаётся разблокированным до завершения его engine; отдельные browser-сессии всё равно проходят собственную проверку пароля. Перезапуск службы снова включает блокировку. Браузерная авторизация не разблокирует обычное desktop-окно.

Обновления machine client проверяются его собственной кнопкой Check updates, а не скрытым SYSTEM-окном. Допустим только новый x64 NSIS-артефакт со свойствами `windows_machine_host: 1`, корректным размером и `digest: sha256:…` в нашем HTTPS-feed. После потоковой проверки native helper повторно проверяет размер/хеш и копирует установщик в защищённый каталог, недоступный для записи неповышенному пользователю; запускается только эта копия. До подтверждённого запуска установщика GUI не закрывается. QA-издание не устанавливает production-обновления. Для публикации принятого машинного установщика workflow `publish-self-hosted` требует явного `windows_machine_host: true`; обычная публикация старого desktop-релиза не объявляет его совместимым с SCM.

Временная пользовательская загрузка удаляется до запуска установщика; при отказе запуска удаляется и подготовленная защищённая копия. Уже запущенный установщик сохраняется в защищённом `updates`-кэше службы: GUI завершается и не удаляет исполняемый файл из-под работающего установщика. После завершения установки этот кэш можно очищать отдельно, не затрагивая профили.

Отдельный unsigned QA-установщик прошёл реальную тихую установку от уже повышенного Root, повторное обновление через штатный старый uninstaller и обычное удаление. До и после обновления терминал действительно работал под SYSTEM; файл SQLite, приватная MCP-идентичность и host-конфигурация сохранились. QA-службы, процессы, каталог приложения и отдельные ключи реестра удалены, данные ProgramData сохранены. Это не подтверждает прохождение UAC неповышенным пользователем или безопасную миграцию установленной пользовательской 5.6.12 в production.

Структурированные MCP-команды локального PowerShell в режиме PTY выполняются в дочернем PowerShell без загрузки профилей. Это сохраняет числовой код завершения и не позволяет `exit` закрыть основной терминал; переменные и функции, определённые только в интерактивной PowerShell-сессии, дочернему процессу не передаются. Обычный ввод в терминал не меняется.

Старый раздел отчётов остаётся совместимым с 5.6.11: его разовые heartbeat не означают online. Неподписанные отчёты и `meta.connection.webUrl` не подтверждают личность ПК и не разрешают туннель. Команды install/update/restart через произвольную серверную очередь не выполняются; обновления приложения обслуживаются существующей системой релизов.

MCP отказывает в запуске при отключении администратором или ошибке чтения/создания административного токена. Повреждённый токен не заменяется автоматически; сервер не переходит в режим без аутентификации. Для намеренного перевыпуска удалите только файл `admin-mcp-token` при остановленном приложении.

## Ограничения
- Переменные окружения читает процесс приложения; для защиты от пользователя задавайте их на уровне системы/установщика, а значения по умолчанию фиксируйте в `brand.config.js` при сборке.
- `brand.config.js` целиком попадает в renderer — секретов там быть не должно (поэтому токен MCP генерируется локально).
- Это защита от случайных/UI-правок; локальный администратор ОС может пересобрать или изменить приложение.
