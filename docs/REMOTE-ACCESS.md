# Удалённая работа с Anubis-Security-Tool

Необходимо различать подключение к серверу, доступ к профилю приложения на другом
ПК и показ рабочего стола Windows. Это разные функции и разные способы входа.

| Задача | Способ |
| --- | --- |
| Подключиться из Desktop к серверу | Закладка SSH, RDP или VNC с адресом сервера |
| Открыть Anubis на одобренном удалённом ПК | Админ-панель → Managed devices → Open device |
| Выбрать профиль на ПК, где запущен Windows machine client | Локальный native GUI и его выбор Windows workspace |
| Увидеть и управлять рабочим столом Windows | RDP либо VNC, а не выбор SYSTEM в Web |
| Открыть удалённый managed-профиль прямо в native GUI по UUID | Такой способ в текущем machine client не реализован |

## Desktop: SSH, RDP и VNC

На компьютере оператора:

1. Запустите Desktop. Откройте меню приложения и выберите **New bookmark**.
2. Выберите нужный тип подключения: **SSH**, **RDP** или **VNC**.
3. Укажите адрес целевого компьютера и порт его службы. Стандартные порты:
   SSH — 22, RDP — 3389, VNC — 5900; фактическая конфигурация может отличаться.
4. Укажите учётные данные целевой службы. Для SSH можно использовать ключ.
   Сохраните закладку и откройте подключение.

**Quick connect** — поле строки подключения, а не отдельный выбор типа.
Например, без включения пароля в URL:

```text
ssh://operator@server.example:22
rdp://operator@server.example:3389
vnc://server.example:5900
```

Служба должна быть включена на целевом компьютере и доступна по разрешённому
сетевому маршруту, например через VPN. Одной установки Anubis недостаточно,
чтобы включить Windows RDP или VNC-сервер. Не открывайте эти порты в Интернет
только ради проверки и не отключайте проверку SSH fingerprint или сертификата.

Протокольные ссылки `ssh://`, `rdp://` и `vnc://` также могут передаваться
в установленное приложение, если Windows разрешила соответствующую ассоциацию.
Не помещайте пароли в ссылки или аргументы командной строки.

В Windows machine client внешняя ссылка, параметры запуска или файл `.vv`
перед подключением дополнительно подтверждаются кнопкой
**Open requested connection**. Диалог показывает Windows account, SID и session
выбранного workspace: именно этот профиль будет выполнять подключение.
Если профиль заблокирован, сначала требуется его пароль приложения.
Это не выбор другого managed-устройства по его UUID.

## Web: профиль приложения на удалённом ПК

На другом компьютере оператора:

1. Откройте <https://api.anubis.locker/admin> и войдите административным токеном
   management API. Не используйте вместо него пароль Windows или ключ MCP.
2. В **Managed devices** найдите нужный экземпляр. Он должен быть **approved**
   и **Online**. Для новой регистрации сначала независимо сверьте полный
   fingerprint с целевым приложением и подтвердите именно этот экземпляр.
3. Нажмите **Open device**. Админ-панель выдаёт одноразовый билет, который
   обменивается на браузерную сессию на отдельном HTTPS-поддомене устройства.
   Простое копирование URL в другой браузер не переносит авторизацию.
4. Если совместимый Windows host показывает **Windows workspace**, выберите
   нужную Windows account/SID/session. **Refresh** обновляет список доступных
   контекстов; это не команда сброса пароля или авторизации.
5. Если выбранный профиль защищён паролем Anubis, введите его существующий
   пароль приложения. Это дополнительная проверка, отдельная от входа
   в админ-панель.

`NT AUTHORITY\SYSTEM | S-1-5-18 | session 0` обозначает служебный контекст
Windows. Это не рабочий стол вошедшего пользователя и не его закладки.
Для пользовательского профиля нужен доступный контекст соответствующего
Windows account/SID/session; нельзя подменять его SYSTEM, если он недоступен.

После входа терминалы и серверные подключения SSH/RDP/VNC выполняются
на целевом компьютере в выбранном профиле. Браузер оператора показывает интерфейс
Anubis, а не изображение экрана этого компьютера. Для изображения рабочего стола
нужен отдельный RDP/VNC-сеанс. Вкладка веб-сайта по HTTP/HTTPS работает иначе.

## Web: вкладка веб-сайта и кнопка Open

В Web-версии обычная вкладка HTTP/HTTPS показывает сайт в `iframe`
браузера оператора. Запрос сайта идёт из этого браузера и его сети:
это не отдельный Chrome, запущенный под выбранным Windows workspace.

Сайт может запретить такое встраивание заголовком `X-Frame-Options` или политикой
`Content-Security-Policy: frame-ancestors`. Кроме того, браузер может блокировать
HTTP-сайт внутри HTTPS-приложения как mixed content. Это не повод обходить
защиту сайта, отключать проверки сертификатов или пароль профиля.

В таком случае используйте существующую кнопку **Open**: сайт открывается
отдельно в браузере оператора, не на удалённом Windows-компьютере. Для обычного
сайта, разрешающего встраивание, содержимое отображается прямо во вкладке.

## Что пока нельзя обещать

Native machine client подключается к локальному защищённому broker и локальному
endpoint выбранного workspace. В нём нет готового выбора произвольного удалённого
managed-устройства из админ-панели. Для такого устройства используйте описанный
Web-путь либо обычное SSH/RDP/VNC-подключение к его сетевой службе.

**Browser Control** в текущем сгруппированном меню относится к объявленным
PRO-заглушкам. Нажатие не запускает Chrome на удалённом ПК. Это не неисправность
кнопки **Open device** и не доказательство доступности автоматизации браузера.
Не путайте этот пункт с обычной вкладкой веб-сайта по HTTP/HTTPS: если не
открывается такая вкладка, это отдельный сценарий, а не поведение PRO-заглушки.

Standalone Web-установка — отдельный экземпляр приложения со своим профилем.
Открытие её главной страницы не подключает автоматически профиль произвольного
Windows-компьютера.

## Долгая загрузка и повторный вход

Постоянные зависания после появления выбора workspace и сбросы входа каждые
несколько минут не являются ожидаемой последовательностью работы.
30 секунд относятся к одноразовому входному билету, а не к необходимости
заново открывать приложение каждые 30 секунд.

Новый вход ожидаем после явного выхода, отзыва доступа, истечения выданной
сессии или перезапуска шлюза, который хранит браузерные сессии в памяти.
Смена пароля профиля также отзывает его браузерную авторизацию.
Если ничего из этого не происходило, следует искать причину сбоя, а не отключать
проверку пароля или бесконечно выдавать новые билеты.

Для диагностики достаточно времени сбоя, версии клиента, адреса без токенов,
выбранного SID/session и статуса HTTP-запроса. Не публикуйте management-токен,
cookies, пароль приложения, Windows-пароль или URL с секретными параметрами.
